cmd / batch 等价写法性能测试报告

为 MAL 完全重构提供量化决策依据 · 测试日期 2026-08-21 · batplayground/perf
重要方法学修正（产生过假数据的坑）：batch 测试脚本若包含 UTF-8 多字节字符（如中文注释）， cmd 解析会出错导致被测循环并未真正执行子进程，测出"快得离谱"的假数据（t31 由 36ms 假值 → 修正后真实 5049ms， t07 由 22ms → 真实 22642ms）。测试脚本必须保持纯 ASCII。runner 现已内置自动拦截非 ASCII 脚本。

给 MAL 重构的直接建议

  1. 热路径全部用「括号块 + for /l + 延迟展开」，绝不用 goto 做循环（每圈省 ~2.3 倍）。
  2. GC / 局部变量清理用「已知下标索引直写」（for /l %%j ... do set "K[%%j]="）， 不要用临时文件枚举，更不要用 for /f ('set 前缀') 子进程枚举。
  3. 避免跨文件 call（每 call 起子进程 + 复制整个环境）。MAL 改生成式扁平单文件，热路径内联。
  4. 环境变量保持精瘦、少而局部。 用 setlocal 隔离局部，能用索引数组就不用数千个命名变量。
  5. 用变量字符串做宏分发可行：!cmdline! 执行一条已存命令串 ≈ 原生 set 的 1.1 倍。

六、变量枚举/清理：三大模式的成本对比（MAL GC 关键）

同一目标：处理一组固定数量的已命名变量 K[1..100]，每 pass 处理一遍。三种等价写法：

模式Nµs/passµs/变量相对说明
t32_indexed_direct 推荐10004026.640.31.0xfor /l %%j ... do set "K[%%j]=" 已知下标直写
t30_tempfile_enum 旧架构模式4002122.853.11.32x( set "K[" ) > tmp + for /f 读回（MAL 旧 GC）
t31_subprocess_enum 不推荐4005048.6126.23.13xfor /f ('set "K["') 每 pass 起子进程枚举
横向：子进程枚举（占满3.1格）vs 索引直写（占满1格）示意

解读：子进程枚举因每 pass 都 CreateProcess 新 cmd，是最慢（3.1x）；临时文件枚举次之（1.32x）； 已知下标索引直写最快——前提是能预先知道变量名集合。for /f ('set') 与管道的值在这里被精准量化， 证实 MAL 旧架构「临时文件 GC + 子进程枚举」为大杀器，新架构应改为「生成期已知数组 + for /l 索引直写」。

七、环境膨胀的隐性代价

用例Nµs/op对比含义
t14_bigenv_set5000329.4normal set 41.7µs →  x7.9 环境膨胀 3000 变量后，普通 set 变慢 ~8 倍
t13_bigenv_enum15016460.8—在膨胀环境上做子进程枚举 → 更慢
t15_bigenv_call1009743.9call 2868 →  x3.4 跨文件 call 拷贝膨胀环境显著变慢

解读：环境变量越多，set、枚举、跨进程 call 全部变慢。MAL 旧架构为了存数据结构塞进大量命名变量， 把环境撑到很大，雪上加霜。新架构应控制环境规模：临时/局部数据用 setlocal 隔离，热数据结构用紧凑的关键（少而短的命名）。

八、新增假设实测（第二轮）

8.1 去除 PATH 能否提速？——仅影响外部工具解析，内部命令无影响

用例µs/次说明
t40_path_empty（PATH 为空）10357以全路径调 where 解析「不存在的命令」，空 PATH 秒失败
t41_path_long（PATH≈1000 目录）15261114.7x 长 PATH 让外部名解析多扫约 1000 个目录

解读：cmd 只为「外部程序/裸名命令」扫描 PATH；set / for / if / echo 等内部命令根本不触发 PATH 扫描。 所以对以内部命令为主的热路径（MAL 就是），剪短 PATH 无任何收益。只有当你按裸名高频调用外部工具 （如 findstr、reg…）且 PATH 极长时，裁剪才可能带来提升——但那已是子进程绑定的调用，收益有限。

8.2 setlocal /? 各开关能否提速？——不能，成本固定

用例µs/作用域对
t42_setlocal_plain（无开关）200
t43_setlocal_full（+EnableExtensions +EnableDelayedExpansion）199
t44_setlocal_extonly（+EnableExtensions DisableDelayedExpansion）201

解读：三种开关组合差异可忽略（200/199/201µs，与上轮 t06=244µs 属同量级）。 setlocal 的成本主要是「复制/恢复环境表」本身，而不是开关翻转。想省钱只能少用，改不了单次开销。

8.3 括号扩着一段 vs 不扩——多套一层括号无代价

用例µs/圈µs/set
t45_block_lvl1（20 条 set 直接作 for 体）88844
t46_block_lvl2（20 条 set 再套一层括号）85743

解读：额外套一层括号几乎零开销（857 vs 888µs，在噪声内）。 即「这段要不要用 ( ) 包起来」不影响性能；真正的性能差来自是进括号块（parse 一次）还是 goto 逐行重解析，与括号层数无关。

8.4 文件总行数影响 call/goto 标签定位——显著

用例µs/call说明
t50_label_few（小文件，:work 靠前）2387接近上轮 call :label 2229
t51_label_many（5009 行，:work 在尾部）185047.75x cmd 需前向扫描定位深处标签

解读：文件越大、标签越靠后，call/goto 定位越贵（本测试 5009 行 7.75x）。 这对「生成式扁平单文件」设计是个提醒：扁平单文件虽省了跨文件子进程，但要控制文件总行数， 并把高频调用的子例程标签放在文件靠前位置，避免反复长距扫描。

8.5 其它等价写法（≈ 一次语句的成本基准）

用例µs/次说明
t01 基线（1 条 set）43参照
t52_if_defined（if defined）45存在性检查 ≈ 一次 set
t53_if_string_eq（if "!x!"=="1"）47字符串比较 ≈ 一次 set
t54_seta_arith（set /a C+=1）43算术 无额外惩罚 ≈ 字符串 set
t55_rem_inloop（块内 rem 注释）41块内注释几乎免费

解读：一次 set、一次 if、一次 set /a 都约 40–47µs，互相等价。 块内 rem 注释基本免费（41µs≈一次 set 量级但未额外叠加）。结论：不必为省「一次 if 判断」或「set /a 算术」过度优化——它们都不比 set 贵。
