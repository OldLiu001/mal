# cmd / batch 等价写法性能测试报告

> batplayground → 本仓库（`cmd_batchfile_perf_report`）
> 测试主机：Windows 11 Pro · 测试日期：2026-08-21
> 全套可复现：`perf/` 目录内含微基准脚本 + 自动计时 runner + 原始数据 `results.csv`

本报告量化了批处理（cmd/batch）各种「等价写法」之间的性能差距，为追求速率的 .bat 项目（例如精简一个慢速的解释器架构）提供决策依据。

---

## 0. 结论速览

| 关键结论 | 实测 | 含义 |
|---|---|---|
| goto 循环比等价的括号块 `for` 慢 | **2.26x**（1068 vs 472 µs/圈） | 热循环用括号块 + 延迟展开，禁 goto |
| 跨文件 `call` 比 `call :label` 贵 | **+29%**（2868 vs 2229 µs） | 每 call 起子进程；改生成式扁平单文件 |
| 环境膨胀 3000 变量后普通 `set` 变慢 | **~8x**（42→329 µs） | 环境要保持精瘦 |
| 枚举变量三种写法 | 索引直写 40 < 临时文件 53 < <b>子进程 126 µs/变量</b> | 子进程 `for /f ('set')` 最慢 3.1x |
| `setlocal` 单次 | ~240 µs | 别进热路径；开关选择无差别 |
| **文件越大，`call/goto` 标签定位越贵** | 5009 行文件慢 **7.75x** | 生成文件控行数，高频标签靠前 |
| 去掉 PATH | 内部命令**无收益**（cmd 不为此扫 PATH） | 仅外部裸名工具受影响 |
| `if` / `set /a` / 块内 `rem` | 各 ~41–47 µs ≈ 一次 `set` | 均无额外惩罚，不必过度优化 |

## 1. 背景：cmd 解析模型（先理解再优化）

- 解析以「语句块」为单位：通常**一行一行 parse**；遇到括号 `( )` 则**整个块一次性 parse**。
- **会重复 parse**：`goto :label` 跳回后执行同一行/同一块，会**重新展开并重新 parse**（不缓存）。
- **块内变量定死**：块整体解析一次后，`%VAR%` 已展开为当时值**不可变**；要动态值必须用**延迟展开 `!VAR!`**。
- 推论：用**一个全局括号块**包住热循环，把 parse 开销摊薄为「解析一次、执行 N 次」，配合延迟展开即可兼顾动态性——这是批量性能优化的核心杠杆。

---

## 2. 测试方法论

- 宿主：Windows 11 Pro；PowerShell runner 计时（Stopwatch，毫秒级）。
- 流程：每脚本 warmup 1 次 + 正式测 3 次，取**最小值**（去冷启动噪声）与平均值。
- 指标：`µs/op = min_ms × 1000 / N`，`N` 为脚本头部 `set _N=...` 声明的迭代次数。
- 控制变量：每个脚本只测一个模式。
- 数据：`perf/results.csv`（最终有效版）。

### ⚠️ 方法学坑（重要，容易产生假数据）

**batch 脚本内出现 UTF-8 多字节字符（如中文注释）会让 cmd 解析出错**，导致被测子进程并未真正执行，
- 测出「快得离谱」的假数据——实测案例：子进程枚举 t31 假值 36ms → 修正后真实 5049ms；t07 假值 22ms → 真实 22642ms。

因此**性能测试脚本必须保持纯 ASCII**（注释只用英文）；`run_perf.ps1` 已内置自动拦截非 ASCII 脚本（跳过并告警）。

## 3. 细节结论

### 3.1 控制流：goto vs 括号块

| 用例 | N | µs/圈 | 相对 | 含义 |
|---|---|---|---|---|
| t00_emptyloop | 400000 | 1.3 | 1.0x | `for /l` 空循环体（纯循环开销） |
| t01_loop_baseline | 40000 | 41.7 | — | 括号块内 1 条 `set` |
| t02_paren_block | 5000 | 472.4 | 1.0x | 12 条 `set` 放**一个括号块**，parse 一次执行 N 圈 |
| t03_goto_loop | 2500 | 1067.9 | **2.26x** | goto 循环：每圈重定位 + 逐行重解析 |

结论：单个扁平 `set`（预解析块内）约 **40µs**，循环空转仅 ~1.3µs；goto 每圈都重新定位标签并解析，是纯开销，**比同等工作量的括号块 for 慢 2.26 倍**。

### 3.2 函数调用：call / 跨文件 / setlocal

| 用例 | N | µs/call | 相对 | 含义 |
|---|---|---|---|---|
| t04_call_label | 800 | 2228.6 | 1.0x | `call :noop` 同文件子例程 |
| t05_call_otherfile | 300 | 2867.6 | 1.29x | `call 其他.bat` 跨文件 = 每 call 一个子进程 |
| t15_bigenv_call | 100 | 9743.9 | 4.37x | 跨文件 call + 环境已膨胀 3000 变量 |
| t06_setlocal | 4000 | 244.3 | — | 一次 `setlocal`+`endlocal` 作用域对 |

- 跨文件 call 因每次 `CreateProcess` 新 cmd 并拷贝整个环境，比同文件 `call :label` 贵 ~29%；环境越胖越贵（3000 变量 → 4.37x）。**MAL 旧架构大量跨文件模块调用正踩在此处。**
- `setlocal/endlocal` 单次 ~244µs，是「环境隔离」的价签，别在热循环里频繁进出。

### 3.3 变量操作 & 宏分发

| 用例 | N | µs/op | 含义 |
|---|---|---|---|
| t01_loop_baseline | 40000 | 41.7 | 1 条扁平 set（参照） |
| t10_var_cmdline | 40000 | 45.0 | `!cmdline!` 执行已存命令串（宏分发模型）≈ set 的 1.1x |
| t11_appendstr | 6000 | 101.2 | 字符串追加 |
| t12_plain_copy | 20000 | 81.2 | 变量到变量拷贝 |

结论：用 `!var!` 延迟展开执行预存命令串仅 ~45µs，几乎与原生 set 持平——**「把命令拼成字符串再用延迟展开执行」的宏分发方案，性能上完全可行**。

### 3.4 变量枚举/清理：三种等价写法（GC 关键）

| 模式 | N | µs/pass | µs/变量 | 相对 | 说明 |
|---|---|---|---|---|---|
| t32_indexed_direct | 1000 | 4026.6 | 40.3 | 1.0x | `for /l %%j ... do set "K[%%j]="` 已知下标直写 |
| t30_tempfile_enum | 400 | 2122.8 | 53.1 | 1.32x | `( set "K[" ) > tmp` + `for /f` 读回（旧 MAL GC） |
| t31_subprocess_enum | 400 | 5048.6 | 126.2 | **3.13x** | `for /f ('set "K["')` 每 pass 起子进程 |

结论：子进程枚举最慢（3.1x）；临时文件次之（1.32x）；**已知下标索引直写最快**（前提是预先知道变量名集合）。
MAL 旧架构的「临时文件 GC + 子进程枚举」是大杀器，新架构应改为「生成期已知数组 + `for /l` 索引直写」。

### 3.5 环境膨胀的隐性代价

| 用例 | N | µs/op | 对比 |
|---|---|---|---|
| t14_bigenv_set | 5000 | 329.4 | 正常 `set` 41.7 → **x7.9** |
| t13_bigenv_enum | 150 | 16460.8 | 膨胀环境上子进程枚举更慢 |
| t15_bigenv_call | 100 | 9743.9 | call 2868 → **x3.4** |

环境变量越多，`set`、枚举、跨进程 call 全部变慢。MAL 旧架构为存数据结构塞进大量命名变量雪上加霜；新架构应控制环境规模、局部数据用 `setlocal` 隔离。

### 3.6 第三轮（2026-08-22）：变量数 / 单变量长度 / 小对象抽象 / 行数换变量

> 针对「环境变量数、函数模板抽象」两大隐性成本专项实测（本地盘执行）。复现：`perf/run_perf3.ps1`，明细 `perf/results3.csv`。

#### 3.6.1 变量数是第一成本（趋于非线性）

同脚本（每次 `set` 读已存在值），预先膨胀环境表：

| 环境变量数 | µs/set | 相对 0 |
|---|---|---|
| 0 | 73.3 | 1.0x |
| 1000 | 189.5 | 2.6x |
| 5000 | 1003.6 | 13.7x |
| 9000 | 2249.4 | 30.7x |
| 10000 | 2595.3 | 35.4x |

**环境表 0→10000 变量，单次 `set` 慢 ~35 倍，且增长非线性。** 这是压倒性第一成本。批量解释器须把活跃变量压到几百以内，总环境控制在 **10000 以下，并加运行时探测的阈值兜底**（机器不同容量不同）。

#### 3.6.2 单变量长度（≤8191 硬上限）

| 值长度 | µs/set |
|---|---|
| 16 | 90.2 |
| 1024 | 138.0 |
| 8190 | 443.4 |

长度影响存在（16→8190 约 4.9x），**远小于变量数量影响**。cmd 单变量值硬上限 8191。策略：值尽量短。

#### 3.6.3 小对象：内联 vs 函数模板（关键）

同一「建小对象→写 3 字段→读 1」逻辑（本地盘干净环境）：

| 写法 | µs/obj | 倍率 |
|---|---|---|
| 全内联（括号块直接 set） | 230 | 1.0x |
| 函数模板（`call :NEW`+`call :GET`） | 2628 | **11.4x** |

> 注：在 OneDrive 同步目录里同脚本模板版高达 19.2ms/obj（~80x）——云同步放大每 call 的 IO。**相对关系仍稳健：函数模板对小对象是压倒性劣势。** 短逻辑一律内联；模板只在高频复用且体量够大时保留。

#### 3.6.4 行数换变量（小边界域分发）

| 用例 | µs/op |
|---|---|
| 变量数组调度（`slot[%i%]` 8 槽） | 163.1 |
| 展开行链调度（8 分支 if/else 直写） | 130.9 |

**小边界域（≤8）展开成行链比变量数组快 -20%，且零存储变量。** 行数换变量有效：既省变量又略提速。

#### 3.6.5 附加微探针

- **OneDrive 同步目录放大 I/O**：同一 `call :label` 脚本，OneDrive 同步盘 ~20ms/call，本地盘 ~0.7–5.5ms/call（**~4–29x**）。批量基准**必须在本地盘执行**。
- **变量数量硬上限探测**：`p60_var_max_probe.cmd` 本机实测可创建 **40000+** 短变量（无 32760 字节式硬上限），但按 3.6.1 性能剧烈衰减 → **实用上限定性能而非容量**；`p61` 为更高端审计。

### 3.7 第四轮（2026-08-24）：递归层作用域 / 帧局部隔离机制

> 针对「递归时帧局部数据如何隔离」专项实测（本地盘执行）。复现：`perf/t70~t74_rec_*.cmd`，明细 `perf/results4.csv`。

递归解释器每进一层 `call :rec` 都要「这块数据只属于本帧、出层即弃、互不串扰」。测 5 种隔离形态，在深度 50/100/200 下度量每递归步均摊成本（µs/步）：

| 隔离机制 | D=50 | D=100 | D=200 | 相对 D200 |
|---|---|---|---|---|
| t70 无隔离（纯 call 基线） | 5468 | 4475 | 3776 | 1.00x |
| t71 `.for-var` 域（项目现状） | 5297 | 4870 | 4208 | 1.11x |
| t72 `setlocal`/`endlocal` 帧 | 5987 | 5492 | 4848 | 1.28x |
| t73 全局 index + 间接读 | 11200 | 10802 | 10118 | **2.68x** |
| t74 全局 index（只写不读） | 5599 | 5302 | 4555 | 1.21x |

结论（验证「第三种最快」的预判是否成立）：

- **t71（`.for-var` 域）最贴近无隔离基线（~1.11x）**，几乎不付隔离税 → 项目现状已是该场景最优选之一，**无需弃用**。
- **t72 `setlocal` 帧 ~1.28x**，明显更贵；t06 单层 ~244µs 的价签在此被逐帧摊高。
- **t73 自维护全局 index 并非最快，反而最慢（~2.68x）**——因为它每帧要「动态拼变量名 + 间接读」（`call set` 双解引用），**证伪了「自维护全局 index 最快」的预判**。
- **t74 把「帧局部只写、数据走调用参数」后回落到 ~1.21x**，但代价是把读侧逻辑全部推给调用方、代码更绕，收益有限，不构成替换 t71 的理由。

**落地建议**：递归层作用域维持 `.for-var` 域（MAL parser/reader 现状），**不换 setlocal、更不换全局 index**。要再抠，仅考虑把**纯数据型字段**改走调用参数（t74 思路）；仍需读帧局部时保留 `.for-var`。

> 附：`call :label` 递归栈上限 ~312（`t70_depth_probe`），为深层嵌套解析提供硬约束参考；MAL 解析器设计递归深度不宜接近此值。

## 4. 第二轮新增假设实测

### 4.1 去掉 PATH 能否提速？→ **仅影响外部工具解析，MAL 无收益**

| 用例 | µs/次 | 说明 |
|---|---|---|
| t40_path_empty（PATH 空） | 10357 | 全路径调 `where` 解析「不存在的命令」，秒失败 |
| t41_path_long（PATH≈1000 目录） | 152611 | **14.7x** 长 PATH 让外部名解析多扫约 1000 目录 |

cmd **只为「外部程序/裸名命令」扫描 PATH**；`set/for/if/echo` 等内部命令根本不触发。以内部命令为主的热路径（MAL 就是）剪短 PATH **无任何收益**。

### 4.2 setlocal /? 各开关能否提速？→ **不能，成本固定**

| 用例 | µs/作用域对 |
|---|---|
| t42_setlocal_plain（无开关） | 200 |
| t43_setlocal_full（+EnabledExtensions +EnabledDelayedExpansion） | 199 |
| t44_setlocal_extonly（+EnabledExtensions DisableDelayedExpansion） | 201 |

三种开关组合差异可忽略。**setlocal 的成本是「复制/恢复环境表」本身，不是开关翻转**；想省只能少用。

### 4.3 括号扩一段 vs 不扩？→ **多套一层括号零开销**

| 用例 | µs/圈 | µs/set |
|---|---|---|
| t45_block_lvl1（20 条 set 直接作 for 体） | 888 | 44 |
| t46_block_lvl2（20 条 set 再套一层括号） | 857 | 43 |

真正的性能差来自「进块 parse 一次 vs goto 逐行重 parse」，与括号层数无关。

### 4.4 文件总行数影响 call/goto 标签定位？→ **7.75x，显著**

| 用例 | µs/call | 说明 |
|---|---|---|
| t50_label_few（小文件，:work 靠前） | 2387 | 接近 `call :label` 2229 |
| t51_label_many（5009 行，:work 在尾部） | 18504 | **7.75x** cmd 需前向扫描定位深处标签 |

**文件越大、标签越靠后，call/goto 定位越贵**。扁平单文件虽省了跨文件子进程，但需**控制文件总行数**，并把高频子例程标签放在文件靠前位置。

### 4.5 其它等价写法（≈ 一次语句成本）

| 用例 | µs/次 | 说明 |
|---|---|---|
| t01 基线（1 条 set） | 43 | 参照 |
| t52_if_defined | 45 | 存在性检查 ≈ 一次 set |
| t53_if_string_eq | 47 | 字符串比较 ≈ 一次 set |
| t54_seta_arith（`set /a C+=1`） | 43 | 算术无额外惩罚 ≈ 字符串 set |
| t55_rem_inloop（块内 `rem` 注释） | 41 | 块内注释几乎免费 |

一次 `set`、一次 `if`、一次 `set /a` 都是 40–47µs，互相等价。**不必为省「一次 if 判断」或「set /a 算术」过度优化。**

## 6. 如何复现

1. 保证所有 `*.cmd` 测试脚本为**纯 ASCII**（run 会自动跳过含多字节字符的脚本并告警）。
2. 在 PowerShell 运行：

   ```powershell
   powershell -NoProfile -ExecutionPolicy Bypass -File .\perf\run_perf.ps1
   ```

3. 输出：
   - 控制台 `Format-Table` 汇总（min/avg/µsPerOp）；
   - `perf/results.csv`（数据，供复算/绘制）。
